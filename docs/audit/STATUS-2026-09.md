## G26 — race-based terms never completed with escrow off (FIXED)

Found 2026-09-16, after the rest of this document. Worth reading even though it
is fixed, because it explains a trap in how the two subsystems were coupled.

`queries.record_race_service` — the row that says "this contract served this
race", and the only input to `races_served` — had exactly one caller:
`escrow_ops.charge_race`. That function returns early when
`budget_config.escrow_enabled` is false. So in an escrow-off league no service
row was ever written, `races_served` never moved off `races_served_before`, and
`escrow.is_term_complete` was never true. Race-based contracts stayed `active`
for as long as the league existed and could only be ended by hand with a
release.

`charge_round_for_tier` compounded it: it `continue`d whenever `charge_race`
returned None, so the term-completion block underneath was unreachable on that
path — including for the narrower case of a contract with no holding while
escrow was on for the season, which is exactly what a contract signed before
escrow was switched on looks like.

**Why it was latent rather than live.** Migration 015 backfills
`escrow_enabled = FALSE` only for `budget_config` rows that already exist when
it runs, then sets the column default to TRUE. A fresh install has no such
rows, so every season it creates has escrow on and the bug is unreachable. It
bit only a league that deliberately chose commitment-only — a supported and
documented choice.

**Fix.** Serving a race and paying for it are now separate steps.
`escrow_ops.record_race_served` writes the service row for any contract with a
term, regardless of the setting, and `charge_round_for_tier` runs it before the
money and checks term completion after it. `charge_race` keeps its
self-contained behaviour for direct callers and takes a `service_counted` flag
when the loop has already recorded the row — without that flag it would read
its own caller's row as "already served" and silently skip the charge, which a
test pins.

Completion also now appends a `term_completed` row to `contract_ledger`, a kind
migration 015 declared and nothing had ever written. Before this, a contract
closing with escrow off left no trace anywhere: `settle_holding` returns None
when there is no holding, so the state went `active` → `completed` with no
ledger row and no receipt line. `receipts.render_escrow_outcome` reports
completions that settled no money for the same reason.

## How G2 was fixed

G2 was reported, fixed, and then reported again — twice — which is
itself the useful part of the record. The first fix added
`seed_preset_into_season` so a season created without a preset could be
rescued. It guarded on *tiers or a config row*, and that guard was the
second defect: `add_tier` writes a tier without creating a
`league_config` row, so a commissioner who created a bare season and
then added one tier through Setup → **Tiers** ended up with tiers but
no settings. Seeding refused because tiers existed. The config panel it
redirected to refused because there was no row to edit. Nothing in the
bot could rescue that season.

The fix is to guard on the thing actually worth protecting. The config
row carries the spending cap and the valuation factors that live
contracts were priced against, so re-seeding over one is destructive and
still refused. Tiers are not — they carry no pricing. So
`seed_preset_into_season` now refuses only when a config row exists, and
when tiers exist it seeds the settings and leaves the tiers alone.

Leaving the tiers alone is not politeness, it is correctness.
`f1.seed_season` calls `queries.insert_tier` directly, which does not
apply the rank-order conflict guard `workflow.add_tier` enforces — so
seeding `t1` alongside a hand-built `pro` tier at rank 1 would have left
two tiers sharing rank 1, a state the panel refuses to create. Hence
`f1.seed_settings_only`, which is `seed_season` minus `_seed_tiers`.

The second residual was advice that could not be followed.
`run_valuation` said *"Seed one with the F1 preset first."* and
`show_config` said *"Create a season with the F1 preset to seed one"* —
the latter being the string the finding was originally filed against,
so both reports were right and each named a different one. Both now name
`/market-admin season seed-preset` with the season's own name
interpolated, and both say the tiers are kept.

Two of those messages also told admins to open `/league` → Setup, "which
offers the same thing". It did not: the Setup screen only printed the
typed command. Rather than delete the claim, the panel now has a **Seed
settings** button, enabled exactly while a season has no config row and
disabled once it does. The checklist gained a **League settings** line
too — `setup_complete` had always required a config row, but the
checklist never showed it, so a season with tiers and drivers and no
settings rendered three ticks and an amber embed with nothing saying
what was wrong.

Verified by reverting each of the eight pieces in turn and confirming a
named test fails for each.

## How G4, G6 and G7 were fixed

The three were one theme: an operation that did the database work
correctly and then stopped short of the parts a human depends on.

**G4** was not a missing capability. Moving a driver onto a tier where
that member already holds a row is genuinely not allowed, and should
not be — `drivers` is UNIQUE on `(season_id, tier_id, member_id)` and a
member keeping both a T3 seat and a T2 reserve seat is a supported
setup. The defect was that the refusal arrived as
`asyncpg.UniqueViolationError`. `move_driver_between_tiers` now looks
for the clash before the UPDATE and refuses with the tier's label and
the id of the row already sitting there, so the commissioner can act on
the other row instead. Its raw `SELECT … FROM drivers` was also replaced
with `queries.fetch_driver_by_id`, which is where that SQL belongs.

**G6** could not be fixed where the audit suggested.
`bot/workflow.py::void_active_contract` is the natural place for the
role drop, but that module is deliberately Discord-free and
`roster_ops.drop_from_team` needs a `Guild`, a `Member` and an actor.
So `void_active_contract` now returns a `VoidOutcome` carrying the
team — read *before* the void, while the contract still points at it —
and the two Discord-facing callers do the drop. Both report it in the
confirmation, including when it fails.

The shared helper `roster_ops.drop_from_team_best_effort` exists because
this is the third copy of the same pattern (release and buyout already
had it, inline). It returns the failure reason rather than raising: by
the time it runs the escrow is settled and the ledger is written, so
raising would strand the caller after a completed void. It also returns
a reason for exceptions whose `str()` is empty, which is where the
inline copies would have reported nothing.

**G7** was a one-line omission with a bad failure mode: voiding a
contract a `pending_approval` trade depended on left the trade
unresolvable from any button in the queue. `void_contract` now runs the
same guard `release_contract` does, and — as the tests pin — runs it
before any write, so a refused void leaves the contract `active` with no
`contract_voided` row.

## Method and its limits

Findings were re-traced from source with callers verified by grep; no tests
were run for this pass, so "FIXED" means the wrong behaviour is no longer
reachable in code, not that a test pins it. Two cases where that gap matters:

- **G5** (no global exception handling) is FIXED via
  `bot/main.py::RosterBot._on_app_command_error`, `base.OwnedView.on_error`
  and `base.PanelModal.on_error`, but **no test exercises any of them**.
- **G15** is FIXED because the three race-night views now extend
  `base.AdminOwnedView`, whose `interaction_check` re-runs `is_admin` per
  click — but `tests/test_panel_screens.py::test_every_screen_is_admin_gated`
  walks `bot/ui/*` and does not cover those three views in `bot/cogs/panel.py`.

**G25** was fixed by validation (`workflow.py::find_rank_conflict`, enforced in
`add_tier` and `edit_tier`) rather than by the `UNIQUE (season_id, rank_order)`
constraint the finding asked for. No such constraint exists in `migrations/`,
so a future writer that bypasses those two helpers would reintroduce duplicate
ranks. Today no such writer exists.

### G20 — board refresh stopped claiming posts it had not made

`refresh_board` returned a bool that conflated "edited", "posted",
"nothing to post" and "Discord refused the edit". A board whose edit was
rejected reported success and its stored state looked unchanged, so the
one failure an owner most needs to see was the one case invisible from
board state.

- `bot/market/boards.py` returns a `BoardRefresh(board_id, posted,

### G21 — season activation and carry-over stopped dead-ending

`season activate` left the owner with no idea what came next, and
`season carry-over` would happily run seasons out of order, silently
stranding the older one's contracts.
